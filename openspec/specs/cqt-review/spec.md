# cqt-review Specification

## Purpose
本能力负责常青藤赛事从作品初审到数值评分、汇总复核和晋级的后台评审流程，使管理员能配置明确的评分规则和评委范围，评委仅处理本人有效任务，并使每次分数变更、结果失效及晋级决定都有可追溯的输入版本和责任人。

## Requirements

### Requirement: [FR-001] 作品定性初审

系统 **MUST** 由具有初审权限的管理员对作品执行通过或驳回，记录作品、原状态、新状态、操作者、时间与原因；驳回原因必填。INITIAL **MUST** 为作品定性初审阶段，不生成评委数值评分任务。已删除作品或过期状态版本的操作 **MUST** 被拒绝。

#### Scenario: 初审通过与驳回
- **WHEN** 管理员通过一件有效待审作品，并对另一件填写原因驳回
- **THEN** 分别更新初审状态，记录两条决定；驳回未填原因时不更新作品
- **判据**:接口响应成功或400，复查作品初审状态与审计记录；INITIAL任务列表不产生评分任务

#### Scenario: 初审并发冲突
- **WHEN** 两个管理员基于同一作品旧版本提交不同决定
- **THEN** 只有一个决定成功，另一请求返回409，不覆盖已生效决定
- **判据**:并发响应一个成功一个409，历史中不存在被静默覆盖的决定

### Requirement: [FR-002] 来源与评审对象准备

系统 **MUST** 按作品来源和评分范围幂等准备评审对象：中戏zhongxi为ENTRY，渠道qudao及后台houtai为每名参赛人的PARTICIPANT。新报名与学校导入按服务端当前账号来源写作品；历史作品以已存source_database为权威，不从成员、学校名或客户端参数推断。已被分配、评分或批次引用的对象 **MUST NOT** 自动转换；冲突 **MUST** 显示原因并阻断相关对象进入分配。相同作品 **MUST NOT** 同时以两种有效对象集合重复计分。

#### Scenario: 幂等准备两类对象
- **WHEN** 为中戏三人团体及渠道三人团体连续两次准备对象
- **THEN** 前者只有一个有效ENTRY，后者只有三个分别关联参赛人的PARTICIPANT，两次结果数量不增加
- **判据**:复查有效对象类型、成员关联与唯一键数量

#### Scenario: 已引用对象不被自动转换
- **WHEN** 历史作品的对象集合与其存储来源冲突，且已有评分引用
- **THEN** 返回冲突明细，原对象及评分保持，相关对象不允许被确认分配
- **判据**:准备/分配预览含明确阻断原因，确认返回409且历史关联不变

### Requirement: [FR-003] 赛事阶段与不可变规则版本

系统 **MUST** 按赛事配置INITIAL、PROVINCIAL、NATIONAL阶段，以赛事与code识别，不使用固定阶段ID。数值评分 **MUST** 只用于PROVINCIAL/NATIONAL。阶段规则 **MUST** 包含综合分范围、最低有效评委数、开放状态及按赛项适用的维度；分数范围合法且最低人数至少1。每次保存规则 **MUST** 产生不可变revision，不覆盖历史评分引用的规则版本。

#### Scenario: 规则变更保留旧版本
- **WHEN** 管理员保存新维度或综合分范围
- **THEN** 新增规则revision，旧评分仍可查询其原始规则，受影响预览和派生结果需重新校验
- **判据**:旧revision内容不变；新revision号递增；旧预览确认返回409

#### Scenario: 不合法阶段配置
- **WHEN** 提交最低人数0、分数上下界倒置，或为INITIAL创建数值任务
- **THEN** 拒绝并说明参数或阶段冲突，不写入有效规则/任务
- **判据**:接口400/409且对应有效数据数量不变

### Requirement: [FR-004] 评委身份与范围

系统 **MUST** 复用现有后台用户，不单独维护评委密码；评委范围 **MUST** 明确赛事、阶段、一级赛项及可选专业/赛区，并验证各引用关系。用户启用状态与updatedAt **MUST** 在每次业务读取、预览及确认时经UserService重新校验，业务不得直接访问sys_user。发现用户禁用或updatedAt变化时 **MUST** 惰性标记受影响结果/预览STALE并拒绝旧预览；本能力不依赖跨模块事件或worker，不保证用户变化瞬间主动刷新所有业务状态。具有按钮权限但不属于有效范围或没有本人有效任务的用户 **MUST NOT** 读取或评分该对象。

#### Scenario: 按范围过滤
- **WHEN** 评委仅获准某届省审的指定赛项及赛区
- **THEN** 其它届、国审、其它赛项/赛区对象均不可分配给该评委；跨范围直接请求被拒绝
- **判据**:预览显示越界原因，直接详情/提交返回403或404且无分数写入

#### Scenario: 用户变化后的惰性失效
- **WHEN** 已生成分配或汇总预览后，基座用户被禁用或updatedAt变化，再次业务读取或确认
- **THEN** 经UserService识别变化，将受影响派生状态标STALE并拒绝旧预览；不需要等待或声称存在跨模块事件worker
- **判据**:基座状态变化后首次业务请求可观察STALE/409；旧hash无法继续确认

### Requirement: [FR-005] 分配预览与确认

系统 **MUST** 对手动及自动分配都执行预览hash确认，预览绑定规则/对象/评委范围与任务输入版本。自动分配 **MUST** 只使用匹配scope的启用评委，以当前有效负载及userId作确定性排序，为每个对象安排指定人数。缺人、越界、重复或冲突 **MUST** 返回逐项清单；确认时任何缺人或冲突 **MUST** 拒绝整次确认，不能静默跳过。阶段、对象、评委组合 **MUST** 唯一；确认须重新校验输入及预览hash。

#### Scenario: 自动分配缺人
- **WHEN** 某对象需要3位评委但有效范围内只有2人
- **THEN** 预览标出该对象缺1人；确认失败，不产生部分静默分配
- **判据**:预览缺人清单包含对象及数量，确认409，任务数量不增加

#### Scenario: 确定性与过期预览
- **WHEN** 相同输入连续预览，随后范围发生变化再确认旧hash
- **THEN** 两次预览分配相同；旧hash确认被拒绝，要求重新预览
- **判据**:目标到评委映射完全相同；变更后确认409

### Requirement: [FR-006] 本人任务与评分提交

系统 **MUST** 只允许当前登录评委访问本人未取消且范围有效的任务；评分详情提供作品附件、目标信息、当前规则、本人草稿与修订。评委 **MUST** 独立填写综合分；所有启用维度的分数与评语 **MUST** 完整且范围合法，综合分不由维度自动求和。系统 **MUST** 支持草稿和提交，只有提交的有效综合分参与汇总。开放且未冻结的任务 **MUST** 允许修订并保留不可变历史；关闭、冻结或过期版本的提交 **MUST** 拒绝。

#### Scenario: 综合分独立于维度
- **WHEN** 评委填写合法维度分与评语，并填写不同于维度合计的合法综合分提交
- **THEN** 保存原维度记录与独立综合分，不强制改成维度合计
- **判据**:重新读取详情，维度值、综合分及修订快照与提交一致

#### Scenario: 非本人及冻结任务
- **WHEN** 评委访问另一人任务，或在阶段关闭后提交本人任务
- **THEN** 前者403/404，后者409，均不修改分数
- **判据**:响应码及评分revision数量不变

#### Scenario: 草稿与并发修订
- **WHEN** 一个任务只有草稿，或两个请求以同一版本修订已提交评分
- **THEN** 草稿不计入有效人数；并发只有一个更新成功，另一请求409，原历史可查
- **判据**:汇总预览有效人数与响应码、修订版本链一致

### Requirement: [FR-007] 汇总预览与确认

系统 **MUST** 在管理员先关闭该阶段评分后才允许汇总预览和确认。预览 **MUST** 包含该阶段全部候选对象，并区分达到minimum的可汇总子集与人数不足、失效对象；达到最低有效人数即可汇总，不要求全部已分配评委完成，但须展示缺评。确认 **MUST** 只为达标子集生成有效final，对未达最低或失效对象的已有final标记STALE并保存缺评/跳过快照，不生成有效分；只有显式`acknowledgeSkipped=true`才允许在存在跳过对象时冻结本次汇总，0个达标对象 **MUST** 拒绝确认。汇总 **MUST** 对同一评委去重，仅取有效任务当前已提交综合分，以BigDecimal算术平均HALF_UP保留两位。确认 **MUST** 锁定phase行并校验inputVersion、规则revision及预览hash；任何输入漂移 **MUST** 整批409且无部分新有效结果。

#### Scenario: 达到最低人数汇总
- **WHEN** minimum为2，分配3人，其中2人提交80.00和81.01，阶段已关闭
- **THEN** 预览显示有效2人、缺评1人，确认得分80.51，保存两个评分输入版本与计算快照
- **判据**:final分数精确80.51，快照可定位两条评分revision，缺评信息不丢失

#### Scenario: 部分达标的显式确认
- **WHEN** 关闭阶段后全量候选中A达到minimum、B人数不足且已有旧final
- **THEN** 预览展示A可汇总、B跳过及原因；缺少acknowledgeSkipped=true时拒绝冻结；显式确认后仅A有新有效final，B旧final为STALE并保留缺评快照
- **判据**:两次确认分别409和成功；A有效结果与B状态/快照可查，无B新有效分

#### Scenario: 全部未达标或输入漂移
- **WHEN** 全部候选未达最低人数，或全量预览后任一评分、任务、用户状态、规则发生变化
- **THEN** 0达标不能确认；输入漂移整批409，不产生部分新有效结果，受影响旧final为STALE
- **判据**:响应409、无新有效汇总结果，STALE状态及原因可观察

### Requirement: [FR-008] 重开与管理员更正

系统 **MUST** 将重开阶段及管理员更正设为独立权限操作，原因必填，记录前后状态/分数、操作者与版本。重开或修改评分输入 **MUST** 使关联final和受影响确认奖项批次STALE；直接更正final **MUST** 生成可追溯的新结果版本并使关联旧奖项批次STALE。任何操作 **MUST NOT** 改写原始评分和历史快照，不得自动重新评奖。

#### Scenario: 更正已评奖成绩
- **WHEN** 管理员带原因将最终成绩从85更正为86
- **THEN** 保存旧85及新86版本、更正原因，原关联批次STALE，不自动变更奖项名
- **判据**:历史含前后值与责任人；批次状态STALE；无新CONFIRMED批次产生

#### Scenario: 重开评分阶段
- **WHEN** 管理员带原因重开已汇总阶段
- **THEN** 相关final及奖项批次标记STALE，后续评分修订保留旧历史，重新关闭后需新预览确认
- **判据**:状态与revision链可查询；旧预览确认409

### Requirement: [FR-009] 晋级预览与确认

系统 **MUST** 支持显式名单或分数阈值产生晋级预览，并由管理员人工确认；范围须限定同赛事同阶段的有效对象与成绩。SHARED模式 **MUST** 以原target进入国审，不复制作品。SEPARATE模式 **MUST** 只生成资格记录，不复制作品、不绕过国赛报名或替用户创建报名；独立国赛报名创建不属于本能力，但系统 **MUST** 支持将已经存在的国赛目标关联到资格，验证同赛事、作品来源、赛项及规范化证件集合精确匹配；不匹配、已被其它目标消费或版本冲突不得关联，匹配凭据只作服务端比对，不向列表或日志公开证件。重复确认 **MUST** 幂等。

#### Scenario: 两种赛事模式
- **WHEN** 管理员确认SHARED及SEPARATE赛事的省审晋级名单
- **THEN** 前者复用原target生成国审可用状态，后者只产生资格；两者均不新增作品或参赛唯一键
- **判据**:晋级记录可查，作品/成员/报名唯一键数量不变，SHARED国审target ID与原ID相同

#### Scenario: 已有国赛目标关联资格
- **WHEN** SEPARATE赛事已有独立报名产生的国赛目标，管理员将其关联到同赛事来源、赛项和证件集合一致的晋级资格
- **THEN** 关联成功且不复制作品；任一匹配字段不一致、资格已被其它目标消费或版本冲突时409；无证件全文对外返回
- **判据**:资格消费关联指向既有target ID，作品数量不变；不匹配请求无关联写入，JSON及日志不含证件全文

### Requirement: [FR-010] 预览确认幂等与审计隐私

系统 **MUST** 将所有预览token绑定用途、操作者、输入版本、参数hash和30分钟有效期；不得跨用途或跨操作者确认，过期或已失效token不得确认。会影响评分、汇总、晋级或派生结果状态的确认操作 **MUST** 携带有效确认token，不得绕过预览直接执行。系统 **MUST** 对分配、汇总、晋级的确认保存幂等请求键与payloadHash；同键同体返回原结果，同键不同体返回409。所有后台写操作 **MUST** 校验独立权限并写操作日志；业务历史 **MUST** 保留必要责任人和前后版本。列表 **MUST NOT** 返回证件全文，日志 **MUST NOT** 记录证件或评分评语正文。后台页面 **MUST** 与菜单component配对，详情在后台Tab打开。

#### Scenario: 重复确认与隐私
- **WHEN** 对同一预览以同请求键重试相同及不同确认体，并查询任务列表与日志
- **THEN** 相同体不重复写任务/结果，改变体409；列表无证件全文，日志无证件及评语原文
- **判据**:确认记录数量、响应码及实际JSON/日志内容检查

#### Scenario: 预览token用途与期限
- **WHEN** 用户使用另一操作者的token、把分配token用于汇总、使用生成超过30分钟的token，或对影响派生状态的确认不传token
- **THEN** 请求被拒绝且不产生状态变化；当前操作者在期限内使用正确用途和版本token才能确认
- **判据**:无效token请求403/409且无业务写入；有效token按对应业务结果执行

#### Scenario: 嵌套评语与原因不进入日志
- **WHEN** 请求中含评分维度的嵌套comment或更正reason，且该接口记录OperationLog
- **THEN** 业务记录保留授权可查看的必要内容，操作日志序列化结果不含comment/reason正文及证件；无需修改框架日志协议
- **判据**:实际业务历史可读取已授权文本，日志中找不到提交的唯一标识评语和原因原文

普通评分草稿/提交使用expectedVersion和requestKey，不要求先生成评分预览token；上述确认专指已列出的预览后确认动作，不能混为所有写请求。

### Requirement: [FR-011] 作品清单导出与奖项匹配标识

系统 **MUST** 提供独立权限控制的作品Excel下载，明确指定赛事和省审/国审阶段并校验归属，按已生效关键字、来源、初审状态筛选而不受分页限制。工作簿 **MUST** 保留赛事/阶段、作品编号与报名号、评分对象编号和类型、人员级参赛人编号、有效成绩状态及版本，奖项列留空；字段顺序与模板版本按唯一接口契约。中戏每作品一行，渠道/后台每有效参赛人一行；无目标/有效成员及来源冲突 **MUST** 保留可识别问题行，不自动补建对象或合并多人成绩。非有效最终成绩 **MUST NOT** 冒充可用分数。所有标识 **MUST** 以文本单元格写入，用户文本不得作为公式；不得导出证件、手机号或原始评语。单次超过10000行 **MUST** 拒绝而非截断，空结果返回表头。成功直出XLSX，错误沿用后台包络；前端 **MUST** 防重复下载、保留错误上下文，不将错误JSON保存成Excel。该导出 **MUST NOT** 执行奖项导入写入。

#### Scenario: 人员级清单及稳定标识
- **WHEN** 管理员导出含中戏团体作品及两个渠道成员的赛事阶段
- **THEN** 中戏作品一行、渠道成员分别一行，稳定ID为文本；STALE分数为空且保留状态/版本，奖项列为空
- **判据**:工作簿行数与对象映射一致，长ID无精度丢失，未写入任何奖项

#### Scenario: 未准备对象与受限导出
- **WHEN** 作品缺少评分对象、导出超10000行、使用不属于赛事的阶段，或请求者没有export权限
- **THEN** 缺对象作品保留问题行；其余请求分别400/400/403，无部分文件或数据库补建
- **判据**:问题行可辨识，错误不触发浏览器文件保存
